## 一、通用问卷作答（题目格式对应主问卷第 3 节）

> 以普通用户身份作答，保留题目原文。设定人设：**30 岁男性，自由职业（平面设计），MacBook + iPhone**。

### A. 你的用户画像

- A1. 你的年龄段与性别（设定）：30 岁，男
- A2. 你主要用什么设备、什么浏览器？：MacBook（Chrome）为主，iPhone（Safari）为辅
- A3. 你平时上网找东西，习惯用什么？：搜索引擎（百度/Google）+ 浏览器地址栏自动补全 + 收藏夹；设计类常用站（Behance、字体站）自己心里记着几个，很少用导航站

### B. 场景与现状

- B1. 回忆最近一次你想找一个"常用网站"（查快递、找工具、看资讯）的完整过程：你具体做了什么？花了多久？：上周想找个"免费商用字体"下载站。百度搜"免费商用字体 下载"，前几条是推广，点进一个网站，下载按钮是假的（诱导点广告），试了两个才找到真站；后来发现收藏夹里其实存过类似的站，但没整理找不到。来回折腾快二十分钟。
- B2. 你现在用网址导航或浏览器书签吗？是怎么组织的？会乱吗？：书签存了 200+ 个，从不整理；实际找站靠浏览器地址栏自动补全——输入关键词浏览器会联想，所以我其实很少需要"导航站"。
- B3. "找网站"这件事，你最烦的是什么？：① 搜索结果广告多、假下载按钮多；② 收藏夹越攒越乱等于没用；③ 有些常用站换了域名就再也找不回来。

### C. 第一印象与理解

- C1. 打开 zhengxie.com.cn 的第一眼感受是什么？（视觉、风格、气质）：红金白，干净、体面，比满屏小广告的导航站高级不少，第一印象是好的。
- C2. 只看首页、不做任何操作：你觉得这站是干嘛的？给谁用的？：像"整理好的常用网站大全"，但"政协/机构"分类让我感觉它主要服务政务相关人群，通用分类又像面向所有人——**两种感觉同时存在**。
- C3. 最吸引你的一点是什么？最想关掉的一点是什么？：吸引我的是视觉干净、分类滑道交互顺；**想关掉的是：卡片文字选不中、复制不了网址**（我想复制某个官网链接发群里，结果选不了，很烦）。

### D. 体验与意愿

- D1. 试着用这站找一个你真正想找的网站：过程顺不顺？卡在哪一步？：试找"免费商用字体"——没收录就扑空；另外**长标题/描述只能横向滚动**，鼠标还行，手机上一行字左右划，体验不太好。
- D2. 你会把它设成浏览器首页或常用导航吗？（1–5 分，说明理由）：2 分。我习惯地址栏自动补全了，普通导航站对我价值不大；除非它变成"我能自定义内容的启动页"，否则不会设首页。
- D3. 它放广告，你会反感吗？如果内容更全、无广告，你愿意付一点钱吗？：顶部一个广告位能接受，但**广告插入如果导致页面布局跳动会很烦**；付费不会。
- D4. 一句话总结：你会怎么向朋友介绍这站？："一个挺体面的常用网站大全，适合不想记网址的人；我自己还是习惯浏览器自动补全。"

## 二、圆桌总结（综合之前所有答卷 + 自己的思考）

我读了第 1、2 位（用户调研专家、产品管理专家）的答卷，两位的判断我基本认同，特别是**定位漂移**（对外说政务垂类、首页是全量通用）和**"可信垂类"作为主战场**的方向。作为开发专家，我先把两位抛来的技术问题接住，再从工程视角补充几个他们没有覆盖的坑：

**① 回应产品专家的技术落地问题：纯静态架构能不能扛住方案？——能，但"云收藏"要另算。**
产品专家提的"反馈入口、收藏导出、本周上新、定位对齐"逐项评估：
- **定位对齐**（改 meta/OG/JSON-LD + 首页文案）：纯静态改动，无成本，随时可做；
- **"没找到"反馈入口**：静态站也能做——用托管表单服务（如 Formspree/腾讯问卷嵌入），提交落到邮箱/表格，零后端；
- **收藏导出（复制文本/书签 HTML）**：纯前端 localStorage 读取 + 生成文件下载，一两天能做完；
- **"本周上新"**：内容运营问题，加一个栏目区块即可；
- **云收藏（跨设备）**：这是唯一触碰架构天花板的需求——localStorage 是本地存储，跨设备必须后端。**我的建议：先别上后端**，用"导出/导入书签"过渡，等回访数据证明收藏是核心需求，再评估轻量方案（Cloudflare Workers + KV / Supabase 匿名表，静态站可挂）。

**② 补充一个前两位没看到的用户层观察：自动补全正在杀死导航站。**
我以普通用户作答时发现：我（及相当多互联网用户）找网站已经靠"地址栏自动补全 + 记忆关键词"，根本不需要导航站。这意味着**导航站的对手不只是 hao123，还有浏览器本身**。这个观察支持产品专家的结论：通用导航没有护城河，必须做浏览器替代不了的事（可信甄别、垂类全量、时效更新）。

**③ 补充工程侧真实风险（前两位没覆盖）：**
- **第三方脚本负担重**：GA4 + 百度统计×2 + AdSense 加载器 + 2 个全宽广告单元，全部塞在页面里。广告全宽自适应插入是 CLS（布局偏移）的头号来源，直接影响 Core Web Vitals；
- **128 张卡片是单行超长 HTML**：每张卡片一行（含超长描述），人工维护极易出错（漏引号/错标签直接破版），且首包 HTML 体积大、影响 LCP；
- **外部图片不可控**：卡片媒体图大多来自外部域名（如 gov.cn 的 favicon），加载失败靠 onerror 移除，视觉上会空一块，质量参差。

## 三、专业深挖：我的 3 个问题及答案

> 注：这 3 个问题已同步追加到主问卷第 6 节「历届追加问题池」。

- Q1. **纯静态架构的天花板在哪？什么时候必须上后端/服务？**
  A1. 静态站能覆盖：内容展示、筛选、本地收藏、表单提交（托管表单服务）、导出下载。天花板在三个点：① **用户数据跨设备**（云收藏、账号体系）；② **动态/个性化内容**（按用户实时渲染）；③ **写操作服务**（评论、用户生成内容）。当前需求里只有"云收藏"触顶——**判断标准：收藏导出上线后，若用户跨设备收藏诉求强烈（回访数据佐证），再上轻量后端**（Cloudflare Workers + KV 或 Supabase 匿名表，静态站可无缝挂），不要提前为未验证的需求加架构。

- Q2. **页面的性能基线怎么测？LCP / CLS 的风险点具体在哪？**
  A2. 用 Lighthouse（移动端）+ PageSpeed Insights 跑基线，盯三个数：LCP、CLS、TBT。风险点：① **CLS 头号来源是广告**——全宽自适应 ins 插入时没有预留空间，页面会跳；② **LCP 受首包 HTML 体积影响**——128 卡全量渲染，index.html 单行超长；③ 第三方脚本（统计/AdSense）虽已 async，但 GA4+百度×2+AdSense 三套并发仍拖慢 TBT。基线先跑 4 周，目标 LCP < 2.5s、CLS < 0.1。

- Q3. **卡片内容靠"单行超长 HTML 手写/生成"维护，风险和出路是什么？**
  A3. 风险：① 任何一处引号/标签错误直接破版（128 卡 × 多字段，改一次错一次的概率不低）；② 新增卡片靠人肉复制粘贴，字段（站序/分类/type/媒体/标签/链接）漏填错填无法自动校验；③ 描述超长（现有卡片有几百字描述）导致单行 HTML 几千字符，diff/审查困难。出路：**内容与表现分离**——卡片数据收进结构化数据源（JSON/现有表格），构建脚本生成 HTML，并在构建后自动跑校验（HTML 格式、死链、字段完整性、type 分组），改数据不碰 HTML。

## 四、点评 / 修改方案 / 发展方向

### 4.1 点评（现状：好在哪、问题在哪）

**做得对（工程质量在同类静态站里是高的）**：
- **渐进增强扎实**：全部内容静态渲染、JS 只做增强，禁用 JS 页面完整可读可点，SEO 与健壮性兼得；
- **安全意识到位**：搜索高亮做了 escapeHtml 防注入（含 `<` `&` 内容不会破版）；链接 rel 规则按域名分级（nofollow/sponsored/ugc）；
- **性能意识良好**：卡片搜索文本 init 预计算、输入防抖、图片 lazy+async 解码、CSS preload、第三方脚本 async；
- **无障碍基础好**：skip-link、全局 :focus-visible 焦点、aria-pressed/aria-label、键盘快捷键（/ 和 Esc）、prefers-reduced-motion、打印样式；
- **暗色模式实现干净**：CSS 变量切换 + 防 FOUC 内联脚本。

**有问题（工程侧）**：
- **广告导致 CLS 风险**：全宽自适应广告位未预留空间，加载即跳动；
- **首包 HTML 大 + 单行超长**：128 卡全量 + 单行结构，LCP 与可维护性双重受损；
- **外部图片不可控**：跨域图质量参差、失败移除留白；
- **无障碍细节**：卡片 `user-select:none` 阻止复制（普通用户 D1 真实困扰）；长标题/描述横向滚动在移动端难用；滚动按钮组"只显示 1 个"用 class 控制显隐，隐藏按钮仍可被键盘 Tab 聚焦；
- **内容链路无校验**：改一个卡片全靠肉眼，无构建期检查。

### 4.2 修改方案（改哪里 → 改成什么样 → 为什么，标优先级）

- [高] **广告位防 CLS**：给两个 `ins` 容器设 `min-height` 预留空间 + `container` 上下边距，广告填充前不跳版。为什么：CLS 直接伤 Core Web Vitals 和用户体验（我 D3 的体感）。
- [高] **内容链路工程化**：卡片数据收进结构化数据源 → 构建脚本生成 HTML → 构建后自动校验（HTML 格式 / 死链 / 字段完整性 / type 分组 / 结果计数与索引一致）。为什么：128 卡手改是最大的长期维护风险（我的 Q3）。
- [中] **无障碍三项**：① `user-select:none` 改为只作用于滑道容器（或去掉，保留链接可点即可）；② 长标题/描述改两行截断（`-webkit-line-clamp`）替代横向滚动，移动端可读；③ 滚动按钮组隐藏态用 `hidden` 属性或 `tabindex="-1"`，避免键盘聚焦不可见按钮。为什么：a11y 是合规与口碑的底线，且第①点直接解决真实用户痛点（D1）。
- [中] **外部图片管控**：图片加 `width/height` 占位（防 CLS）、统一处理加载失败兜底（现有 onerror 移除可保留，但补一个纯色/文字占位背景），重要卡片的媒体图考虑本地化（转存 WebP）。为什么：视觉质量是"可信感"的一部分。
- [低] **前端微优化**：星形 SVG 每卡内联重复 128 次 → 用 `<use>` 引用或 CSS 背景；统计脚本评估合并（双百度统计 + GA4 可保留但确认无重复埋点）。为什么：降首包体积与 TBT，锦上添花。

### 4.3 发展方向（中短期 1–3 个月 / 长期半年以上）

- **中短期**：① 跑 Lighthouse/PageSpeed 基线（LCP/CLS/TBT）；② 广告防 CLS + 无障碍三项 + 外部图片兜底（三周内可完成的技术债清偿）；③ 内容链路工程化（数据源 + 构建 + 校验），为"本周上新"高频更新打地基；④ 支持产品方案里的反馈入口（托管表单即可）与收藏导出（纯前端）。
- **长期**：① 若云收藏被验证为刚需，评估 Cloudflare Workers + KV / Supabase（静态站可挂，不推翻现有架构）；② 国内访问优化：GitHub Pages 国内不稳定，评估国内 CDN / 对象存储 + ICP 备案（页脚备案占位已留）；③ PWA 化（manifest 已有雏形，补 service worker 离线缓存，导航站适合装成 App）；④ 性能目标：LCP < 2.5s、CLS < 0.1，纳入发布检查。
