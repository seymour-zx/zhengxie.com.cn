## 二、圆桌总结（综合之前所有答卷 + 自己的思考）

我通读了第 1–3 位答卷，并**实际审查了 main.js（621 行）、style.css（800 行）、index.html、404.html、manifest.json 全部代码**。总体结论：**这是一份工程质量高于同类静态站平均水平的代码**，没有 blocker 级安全漏洞，问题集中在"边界情况的处理"和"可维护性"——这正好是我作为审查专家的主场。

**① 认同前三位，并精确一处：上一位说的"滚动按钮隐藏态可被 Tab 聚焦"——经核实不成立。**
`.scroll-btn` 默认 `display: none`，只有 `.is-active` 才 `display: flex`。**`display: none` 的元素不参与键盘 Tab 序**，所以键盘用户不会聚焦到不可见按钮，该问题不存在。代码审查的价值就在这里：宁可查实后说"没问题"，也不人云亦云。

**② 认同"定位漂移 + 可信垂类"：代码层面无阻碍，且我要指出一个安全面的佐证。**
整个站的 XSS 面基本封闭：搜索高亮的 `escapeHtml`、筛选 chip 用 `textContent` 创建、hash 里的分类名用 `CSS.escape`、链接 href 全部来自受控数据源（构建生成）。**没有发现用户可控输入到达 innerHTML/DOM 注入的路径**——这对一个要主打"可信"的政务向站点是重要的安全基线，值得保持。

**③ 补充我的核心发现：一个可复现的高亮 bug + 几处边界风险（详见第四节）。**
最值得先修的是一个**搜索高亮标签破损 bug**：搜索某些字符（如单个字母 k、a、r 或 "mark"、"em" 等）时，`<mark>` 标签本身会被二次匹配包裹，产生无效 HTML（如 `<mar<mark>k</mark>>`）。这直接伤"站内搜索"这个核心功能，且是确定性的逻辑缺陷。

**④ 回应产品/开发方案（代码可行性）：全绿。**
反馈入口（托管表单）、收藏导出（纯前端 Blob 下载）、"本周上新"（静态区块）在现有架构下都可行；云收藏需要后端（上一位已详述），代码层无阻碍。

## 三、专业深挖：我的 3 个问题及答案

> 注：这 3 个问题已同步追加到主问卷第 6 节「历届追加问题池」。

- Q1. **字符串 replace 式搜索高亮有哪些隐藏坑？正确的做法是什么？**
  A1. 三个坑：① **标签二次命中**——`<mark>` 标签文本里的字符（k/a/r/m 等）会被后续关键词的 `replace` 再次匹配，导致标签嵌套、破损（本站在 580–598 行的 `highlightCard` 里真实存在）；② **大小写敏感**——`indexOf` 区分大小写，搜 "github" 找不到 "GitHub"（本站在 95–98 行真实存在）；③ **重叠关键词**——先高亮"百度"再高亮"百度百科"，连续 replace 会互相干扰。正确做法：**占位符保护 + 一次性构建**——先按位置收集所有匹配（匹配原始文本、大小写不敏感），再用一次正则/拼接生成带 `<mark>` 的结果，或先对已插入标记用不可见占位符（如 `\u0000`）保护再统一还原；比较时统一 `toLowerCase`。

- Q2. **这个纯静态站最值得补的自动化"质量闸门"是什么？**
  A2. 按性价比排序：① **构建期校验脚本**（已有数据源/生成链路）：生成后自动查 HTML 格式（标签闭合）、死链、字段完整性（站序/分类/type/链接）、type 分组与结果计数一致性——改一个卡片立刻报错，而不是上线后肉眼找；② **纯函数单元测试**：把筛选逻辑（applyFilter 的三维 AND）、高亮逻辑（highlightCard）、收藏逻辑（favs 增删）抽成无 DOM 依赖的纯函数，跑 Node 单测——这几个是核心行为，现在全靠手点验证；③ **CI（GitHub Actions）**：push 自动跑校验 + 测试 + 简单 Lighthouse 分数门槛，不过就拦截。三件套成本低、收益是"改得放心"。

- Q3. **这个站"看起来安全、其实边界会咬人"的三个点是什么？**
  A3. ① **hash 状态还原的静默失败**：`syncFromHash` 里分类不存在时静默跳过（可接受），但标签含英文逗号（如"SEO,AI"）会被 `split(',')` 拆成两个标签，往返不一致（521–545 行）——边缘但真实；② **localStorage 写入静默失败**：隐私模式下 `setItem` 抛错被 try/catch 吞掉，用户点收藏以为存上了，实际换会话就没了——**没有给用户任何提示**（66–69 行），对"可信"定位是隐性伤害；③ **老浏览器兼容**：hero 标题用 `background-clip:text + color:transparent`，不支持的浏览器（旧 Edge/部分安卓 WebView）标题**完全不可见**，且 `backdrop-filter` 无回退（style.css 143–147、250 行）——政务人群的老设备恰恰是重灾区。

## 四、点评 / 修改方案 / 发展方向

### 4.1 点评（现状：好在哪、问题在哪）

**做得好（值得保持）**：
- **安全基线干净**：XSS 面基本封闭（escapeHtml / textContent / CSS.escape / 受控 href），localStorage 全 try/catch，无敏感信息入客户端；
- **渐进增强教科书级**：全部内容静态渲染、`[hidden]` 兜底、JS 只做增强，禁用 JS 页面完整可用；
- **性能意识强**：卡片搜索文本 init 预计算（`__search`）、150ms 防抖、scroll 被动监听、图片 lazy+async、CSS preload；
- **a11y 基础好**：skip-link、全局 :focus-visible、aria-pressed/label 齐全、`/` 与 Esc 快捷键、prefers-reduced-motion、打印样式（连 404 都自包含且带暗色防闪烁）；
- **代码注释质量高**：复杂逻辑（滚动锁、hash 往返、高亮转义）都有"为什么"级注释，维护者接手成本低。

**有问题（按严重度）**：
- 🔴 搜索高亮标签破损（可复现 bug，见 Q1）；
- 🔴 `favToggle.addEventListener` 无空值保护（其他元素都判空了，这个不一致，某页缺元素会整段脚本崩）；
- 🟡 搜索大小写敏感（英文站名搜不到）；
- 🟡 亮色模式 focus outline 用亮金（白底上对比度 ~1.9:1，键盘焦点几乎不可见，不满足 WCAG 2.4.7）；
- 🟡 `background-clip:text` 无回退（老浏览器标题不可见）+ `backdrop-filter` 无回退；
- 🟡 长标题/描述横向滚动（键盘/移动端不可达，复制难）；
- 🟡 `user-select:none` 禁复制（普通用户 D1 的真实困扰，且违背"让用户能用"的初衷）；
- 💭 细节：`.ad__label` 硬编码色、`onerror="this.remove()"` 内联 handler（未来加 CSP 会失效）、hash 逗号边界。

### 4.2 修改方案（改哪里 → 改成什么样 → 为什么，标优先级）

- [高] **修复高亮标签破损**（main.js highlightCard）：改用占位符保护 + 大小写不敏感的一次性构建（先收集匹配位置，再拼结果）。为什么：核心功能 bug，可复现、确定性。
- [高] **favToggle 判空**（main.js 238 行）：`if (favToggle) { ... }` 与 engine 一致。为什么：防御性编程，防页面缺元素时整段脚本崩。
- [中] **搜索大小写不敏感**：`__search` 缓存时 `toLowerCase()`，比较时同样归一。为什么：英文站名（GitHub 等）可搜。
- [中] **focus-visible 对比度**：亮色改用 `--red`（深红）做 outline 或加深金色，暗色保留亮金。为什么：WCAG 2.4.7 焦点可见是硬性要求，政务人群键盘用户不少。
- [中] **background-clip 兼容回退**：`@supports (background-clip: text) { ... }`，不支持时回退纯 `--red` 文字色。为什么：老设备（我人设里的 360/老安卓）标题不可见是"网站坏了"级别的体验。
- [中] **长标题改两行截断**：`.card__title/.card__desc` 用 `-webkit-line-clamp` 两行截断，替换横向滚动（标签/链接行保留横滚）。为什么：键盘/移动端可达性 + 复制可用。
- [低] **user-select 收窄**：从卡片整体移除，仅保留在滑道内容。为什么：解决真实用户"复制不了网址"的痛点。
- [低] 杂项：`.ad__label` 颜色走变量；hash 标签含逗号时用 encodeURIComponent 全量编码往返；onerror 占位补文字提示。

### 4.3 发展方向（中短期 1–3 个月 / 长期半年以上）

- **中短期**：① 修掉 🔴/🟡 全部（一周内可完成，都是小改动）；② 引入构建期校验脚本（HTML 格式/死链/字段/type 分组/计数一致性），改卡片不再靠肉眼；③ 把筛选/高亮/收藏抽成纯函数 + Node 单测——这是这个站最值得的自动化投入。
- **长期**：① GitHub Actions CI：push 自动跑校验 + 单测 + Lighthouse 分数门槛，不合格拦截发布；② 把 a11y 审计（axe-core）纳入发布检查，避免"新增 UI 破坏对比度/焦点"回潮；③ 若上云收藏（后端），代码审查要重点盯鉴权与数据边界——从"可信"定位出发，数据安全是品牌资产，不是成本项。
