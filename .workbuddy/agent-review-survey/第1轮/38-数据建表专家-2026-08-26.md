## 二、圆桌总结（综合之前所有答卷 + 自己的思考）

**认同什么**
- #21 可信档案、#28 新鲜度、#31 可信分级、#33 守门矩阵、#36 世界圣经——方向全对，且**本质都是"给每条收录加结构化字段 + 规则"**。这正是建表专家的活。
- #37 超级合伙人"减法优先、先把已想清楚的压成 v1"——完全同意；我这一棒就把"可信"压成**一张表该有的列**。

**补充什么（我的核心增量）**
- **圆桌最大的盲区：数据底座其实存在，但 schema 是"裸的"。** #27/#34 说"128 卡全靠人工手写、无数据源文件"——实测**不对**：15 个 `self_links.xlsx` 就是数据源（约 384 条），构建读它生成页面。所以问题不是"建数据源"，而是**这张表缺主键、缺可信字段、缺字典、缺校验、且 15 份碎片化**。这是可立刻修的 Phase 0/1 数据契约，比另建 #34 LLM Wiki 更接地。
- **把"可信/世界观"落成表契约，而非并行系统。** #34 想建独立 wiki、#21 想建后台档案、#36 想建世界圣经——三者若都另起炉灶，会和 xlsx 三套数据互漂（#22 维护可见性告警正中此坑）。正确做法：**xlsx 是唯一真值源**，加列即可；wiki/圣经是它的"视图/派生"，由表生成，不反向存。
- **给 card 一个稳定主键。** 当前 `站序` 是同子分类序号（实测"市政协"下北京/天津都为 2），无全局唯一键 → 去重、增量更新、按卡新鲜度提醒、用户收藏溯源(#25/#35)全部无从做起。补 `id` 列（如 `ZX-GOV-0001`）是撬动 #21/#28/#33 的支点。

**反对什么**
- 反对在 xlsx 未修前先建 #34 独立知识库 / #32 简报 / #30 聚合 CI：上游数据没有 PK 和可信字段，下游每套都得自己重新对齐，重复劳动 + 漂移风险。先把表契约钉死。
- 反对 `links` 列继续"label,url"塞一格：反范式、脆弱、不可校验。

**往哪个方向再推一步**
- 推一步 = **定义一份"收录数据契约"（data contract）**：统一列结构 + 数据字典 + 主键 + 校验脚本。让 #21 档案、#28 新鲜度、#33 守门、#36 收口规则，全部变成"对这张表跑一次校验"就能看见的红/绿，而不是人工读文档。

## 三、专业深挖：我的 3 个问题及答案

> 已同步追加到主问卷第 6 节「历届追加问题池」。

- **Q1. 圆桌 14 棒都在谈"可信档案/知识库/世界圣经"，但实站核验：收录数据早已是 15 个 `self_links.xlsx`（约 384 条），问题不在"缺数据源"而在 schema 裸奔——没有主键、没有可信字段、15 份碎片化。怎么把"可信"从口号落成一张表该有的列（含稳定 `id` 主键 + 来源/核验/失效字段），并是否应合并为一张总表而非 15 份分散工作簿？**
  - **A1.** 两步：① **加列不换表**——在现有 A–H 上扩展可信列（见第四节 4.2【高】schema），先补 `id`(PK) + `source_type`(S/A/B/C/D) + `verify_date` + `verify_channel` + `verify_by` + `status`(active/monitor/expired) + `review_cycle`；② **加一张总表 `directory/_master/all_links.xlsx`** 作为唯一真值源，15 个分类 xlsx 退化为"按分类筛选的视图/导出"（构建仍读分类表，但校验与去重跑总表）。主键 `id` 全局唯一 → 跨分类去重、按卡新鲜度提醒、用户收藏溯源(#25/#35)全部解锁。总表也是 #34 wiki 的源、`#36 世界圣经`的落点。
- **Q2. `links` 列把"label,url"塞一格、`desc` 空 54/65（83%）、`media`(favicon) 空 58/65（89%）、`type` 是未文档化的 {1,3}——怎么设一份"数据完整度 SLA + 发布前校验闸门"，让缺 desc/缺 favicon/缺核验日期的卡**不能**上线，把 #22 维护可见性与 #23 客户关口变成红/绿自动检查？**
  - **A2.** 立三条硬规则 + 一个零依赖校验脚本（纯 Python 读 15 xlsx，详见 4.2【中】）：① **完整度 SLA**——`desc`、`media`(favicon，或无则构建期按域名自动生成)、`verify_date` 三项必填，否则卡标记为 `status=draft` 不进频道页；② **`links` 规范化**——拆成 `link_label` + `link_url` 两列（或 `links` 改为 JSON 数组 `[{label,url}]`），构建期校验 URL 含 `http` 且域名命中白名单；③ **`type` 数据字典**——{1=官网主站,2=办事大厅,3=栏目/资讯,9=其他}写进 `SCHEMA.md`。脚本输出"红灯清单"（缺字段/重复 id/非白名单域名/空核验日期），CI 或人工发布前必过——这正是 #23"先过客户关口"的工程化：不是"测真人"，是"测数据能不能发"。
- **Q3. #36 世界圣经说"收什么不收什么/跟官方啥关系"应是站点真相——怎么把这条真理**编码成表格的录入校验规则**（域名白名单、source_type 枚举、非官方 rejection），让"可信"在录入那一刻就被强制，而非事后 PR？这又如何顺手消 #15/#17 冒充官方风险？**
  - **A3.** 把 #36 的"收口规则"翻译成**表级校验**：① **域名白名单**——`link_url` 必须属于 `*.gov.cn` / 民主党派官方域名（民革/民盟/民建/民进/农工党/致公党/九三学社/台盟中央及省级官网）/ 权威政务平台；非白名单域名的行，校验脚本标红且**不生成卡片**（从源头杜绝仿冒/中介站进收录，直消 #15/#17 冒充雷）；② **`source_type` 枚举约束**——只能填 S/A/B/C/D（#33），填别的报错；③ **`分类` 枚举约束**——只能从世界圣经定义的分类白名单取值，防止 ai/bank 等"全量"残余悄悄回流。录入即合规 → "可信"不再靠人记，离职也不丢。

## 四、点评 / 修改方案 / 发展方向

### 4.1 点评（现状：好在哪、问题在哪）
- **好**：数据底座已存在（15 xlsx ≈384 条），构建读表生成页面/JSON-LD，方向对；8 列基础字段够生成卡片。
- **问题（数据表视角，按优先级）**：
  1. **无主键**（站序非唯一）→ 去重/新鲜度/溯源全废；
  2. **可信字段为零** → #21/#28/#33 要的数据层全缺；
  3. **完整度差**（desc 83% 空、media 89% 空）→ 用户见裸链、弱信任；
  4. **`links` 反范式 + `type` 无字典 + `tags` 混语义** → 不可校验、不可维护；
  5. **15 份碎片化、sheet 名不一致(Sheet/links)** → 无总表、无去重、构建兼容两种命名是 smell；
  6. **无校验闸门** → 改错一格静默出错，#22 维护可见性落空。

### 4.2 修改方案（改哪里 → 改成什么样 → 为什么，标优先级）
- **【高·Phase 0·零后端·可逆】补 `id` 主键 + 可信列（改 15 xlsx 表头/加列）**：在 A–H 后追加 `id`(全局唯一,如 `ZX-GOV-0001`)、`source_type`(S/A/B/C/D)、`verify_date`(ISO)、`verify_channel`、`verify_by`、`status`(active/monitor/expired/draft)、`review_cycle`。**为什么**：这是撬动 #21/#28/#33 的支点；无 PK 一切 per-card 能力免谈。→ 具体补丁见文件末「待授权数据契约」。
- **【高·Phase 0】建 `directory/_master/all_links.xlsx` 总表**：15 分类 xlsx 作为总表按分类筛选的导出/视图；校验与去重跑总表。**为什么**：消灭碎片化、支持跨分类去重与统一审计（#34 wiki 之源）。
- **【中·Phase 1】发布前校验脚本（零依赖 Python）**：遍历 15 xlsx，红灯清单 = 缺 id/重复 id/缺 desc/缺 media/缺 verify_date/非白名单域名/type 越界/分类越界；CI 或人工发布前必过。**为什么**：把 #22 维护可见性 + #23 客户关口变成红绿自动检查，也是"减法优先"里最该先上的质量闸门。
- **【中·Phase 1】`links` 规范化 + `type`/`分类` 数据字典（`SCHEMA.md`）**：`links`→`link_label`+`link_url`（或 JSON 数组）；`SCHEMA.md` 写清每列含义、`type` 枚举、`分类` 白名单、域名白名单。**为什么**：可校验、可交接、消 #36 世界观在数据层打架。
- **【中·Phase 1】补齐完整度 SLA**：`desc`、`media`(无则构建期按域名自动生成 favicon)、`verify_date` 必填否则 `status=draft` 不生成卡片。**为什么**：用户从"裸链"变"带说明+带来源+带图标"的可信卡（治 #37 C3"不敢信"）。
- **【低·Phase 2】表→派生视图**：总表生成 #34 wiki 页、#28 新鲜度流、#30 聚合燃料、#33 守门工作台；表是唯一写入口，视图只读。**为什么**：避免 xlsx/wiki/圣经三套数据互漂（#22 告警）。

### 4.3 发展方向（中短期 1–3 个月 / 长期半年以上）
- **中短期**：Phase 0（主键+可信列+总表）Day 0–2 → Phase 1（校验脚本+SCHEMA.md+完整度 SLA）Week 1 → 每次发布跑校验，红灯不过不发布。先让"可信"在表里可追溯，再谈 UI 徽章(#37 demo)。
- **长期**：总表成站点宪法（接 #36 世界圣经），wiki/新鲜度/聚合/守门全由其派生；配合 #26 埋点测"带来源卡是否真提升设首页意愿"，不符则回滚上层、保表契约。
