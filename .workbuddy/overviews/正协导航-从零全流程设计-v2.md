## 0. 设计总纲

### 0.1 为什么需要这份设计（痛因）

现有项目记录经过多轮圆桌、多份文档、多次修正后出现**记录互斥**，典型：

| 互斥示例 | 记录 A | 记录 B |
|---|---|---|
| 官方认证标记 | C 组待办 ⬜ | 已决取消（逐卡标记不成立，可信=整站级） |
| 卡片真值源 | `self_links.unified.xlsx` | 实际 `cards.unified.xlsx` |
| 分流列 | `scope` | 实际 `dir_path` |
| 频道数量 | "15 频道" | 实际 2 频道 + 1 hub |
| 卡片列数 | "英文 75 列" | 实际 32 列 |

根因：**多份文档各自为政、无统一决策库、文档不随事实更新**。修补单处无效，必须重建一套自洽体系。

### 0.2 设计原则（本设计的不可违背项）

1. **单一权威源**：数据、文档、决策各只存在一份权威；其余一律指针或派生。
2. **决策编号化**：每条已拍板决策入决策库（§9 DEC），可追溯、可推翻、可回滚；清单不再出现"已决事项仍标待办"。
3. **以实际资产为事实**：一切设计以仓库实际文件、实际数据为基准，不以旧文档表述为据。
4. **静态优先**：GitHub Pages 无后端；能力边界外的事（表单送达、账号体系）明确标注"不做"，不做静默假象。
5. **可信=整站级**（DEC-005）：不渲染逐卡认证徽章；可信信号=来源透明（链接露真域名）+ 整站声明 + 机器可读 Organization。
6. **最小文档集**：文档宁缺毋滥，每份只写一次、只写增量；新记录进时间日志，不新建"第 N+1 份说明文档"。

### 0.3 全流程地图（8 环节闭环）

```
① 产品定义 → ② 数据建模 → ③ 构建生成 → ④ 质量校验 → ⑤ 部署发布
    ↑                                                          ↓
⑧ 反馈迭代 ← ⑦ 收录与内容 ← ⑥ 运营监控 ←─────────────────────┘
```

- 每一轮改动：从 ⑧ 进入，回到 ① 更新决策库 → 沿链路走一遍 → 落 ⑤。
- 治理纪律贯穿全链：先记日志再动手、备份可回档、agent 不执行 git、公开层不暴露工作流（§8）。

### 0.4 权威源结构（解决"记录衔接不上"）

| 层 | 文件 | 职责 | 谁维护 |
|---|---|---|---|
| L0 唯一权威 | **本文件（v2.0 设计总纲）** | 定义一切环节与契约 | 执行负责人 |
| L1 决策库 | 本文件 §9（DEC 表） | 全部已拍板决策，集中登记 | 执行负责人 |
| L2 执行手册 | `README.md`（公开层教程）+ `assets/.build/`（脚本） | 怎么写站、怎么跑构建 | 执行负责人 |
| L3 日志 | `.workbuddy/memory/YYYY-MM-DD.md` | 当日原始事件流（append-only） | 执行负责人 |
| L4 快照 | `.workbuddy/memory/backup.md` + `backups/` | 全空间备份、回档点 | 执行负责人 |

**旧文档处置（建议，用户拍板后执行）**：`.workbuddy/docs/` 现有 20 份编号文档 + `CONVENTIONS.md` 属旧体系产物，v2.0 生效后**整体降级为历史归档**（保留不删，移入 `.workbuddy/archive/2026-08-29-before-v2/`），不再作为执行依据；其中仍有价值的内容（如 §3.1 JSON-LD 契约、测试八项定义）已吸收进本文件对应环节。降级动作走 §8 纪律（先备份、记日志、列清单待确认）。

## 1. 环节 ① · 产品定义

### 1.1 定位（一句话）

> 民间独立运营的政协垂类导航站：只收录**经核验的官方公开入口**，链接直达官网、域名可见，让办事人找到并确信"是真的"。

### 1.2 目标用户

办事群众（怕被骗）、政协委员/党派成员（高频入口）、政务工作者（检索工具）。

### 1.3 边界（做什么 / 不做什么）

| 做 | 不做 |
|---|---|
| 收录经核验的官方公开入口 | 代办、代开、加急、包过、贷款、下载器（负面词 D 组，永久屏蔽） |
| 索引聚合 + 来源透明 | 冒充官方、使用官方标识/视觉、自称官方 |
| 政务频道零广告；非政务频道广告须与内容明确区隔 | 站内生成政务/民生资讯（聚合≠生成，发布前人工守门） |
| 整站级可信信号 | 逐卡认证徽章、逐卡核验日期（DEC-005） |
| 反馈收集（渠道明确、不静默丢失） | 无后端却假装"提交成功"（DEC-009） |

### 1.4 页面契约（固定 14 页）

| 页面 | URL | 类型 | 生成方式 |
|---|---|---|---|
| 根页 | `/` | 导航首页 | build 自动 |
| 404 | `/404.html` | 错误页（noindex，**不加 canonical**，DEC-011） | 手写 |
| 频道 hub | `/directory/` | CollectionPage | 手写 |
| 引擎频道 | `/directory/engine/` | WebPage | build 自动 |
| 政务频道 | `/directory/gov/` | WebPage | build 自动 |
| 关于本站 | `/pages/about/` | AboutPage | 手写 |
| 联系我们 | `/pages/contact/` | ContactPage | 手写 |
| 使用指南 | `/pages/guide/` | WebPage | 手写 |
| 网站全景 | `/pages/overview/` | WebPage | 手写 |
| 站点地图 | `/pages/sitemap/` | WebPage | 手写 |
| 收录申请 | `/pages/submit/` | WebPage | 手写 |
| 隐私政策 | `/pages/privacy/` | WebPage | 手写 |
| 免责声明 | `/pages/disclaimer/` | WebPage | 手写 |
| 更新日志 | `/pages/changelog/` | WebPage | 手写 |

新增页面规则：先入决策库（DEC-xxx）→ 定 JSON-LD 类型 → 按 §7 收录/构建流程落地 → 更新本表。**禁止裸新增**。

### 1.5 JSON-LD 契约（每页必守）

- 类型：按上表；所有页 `isPartOf` 统一回链站点根 `WebSite`（`https://zhengxie.com.cn/`）。
- 面包屑：真实层级，不虚构（`首页 › 网站全景 › 子页`，hub 与 overview 是兄弟非父子）。
- 根页 `WebSite` + `SearchAction`；about 页另带 `Organization`（整站级机器可读可信声明，DEC-005 载体）。
- 404 页不加 JSON-LD、不加 canonical（DEC-011）。

### 1.6 head 模板契约（每页必含 13 项）

`title` / `description` / `keywords` / `canonical`（404 豁免）/ `og:title` / `og:description` / `og:image` / `og:site_name` / `og:url` / `twitter:card` / `theme-color` / `viewport` / `apple-touch-icon` / FOUC 防护内联脚本。

## 3. 环节 ③ · 构建生成

### 3.1 脚本职责边界（各管一段，不越界）

| 脚本 | 职责 | 输出 |
|---|---|---|
| `build.py` | 编排入口，按序调用，失败即中断 | 退出码 |
| `build_homeplus.py` | 读 xlsx → 生成根页 + 频道页（JSON-LD、head、卡片） | `index.html`、`directory/<name>/index.html` |
| `collect_meta.py` | 采集全站 title/keywords/description | SEO 报告 xlsx |
| `check_links.py` | 死链检测（数据源 `cards.unified.xlsx`，报告进 `assets/.build/reports/`） | link_report |
| `sync_star_sprite.py` | 收藏星形 SVG sprite 同步 | svg 资源 |
| `verify_site.py` | L1 静态校验八项（红线 exit 2 / 严重 1 / 全过 0） | 控制台报告 |

### 3.2 构建链路（每次改动必走）

```
改 xlsx/模板 → python assets/.build/build.py → 生成全部页面 → verify_site.py 全绿？
    → 是：check_links.py 抽查 → 上线清单 → 部署
    → 否：阻断，修复后重跑
```

### 3.3 产物与源码分离

- 生成产物（`index.html`、频道页）可进 Git 随仓库同步（用户已定方案甲）；源码脚本与 xlsx 是编辑对象，产物是只读结果。
- 备份永不进发布层/资源层（进 `.workbuddy/backups/`）。

## 4. 环节 ④ · 质量校验

### 4.1 分层测试（L1–L5）

| 层 | 工具 | 时机 |
|---|---|---|
| L1 静态扫描 | `verify_site.py` 八项（断链/head/外链属性/链接合法性/图片/标题层级/JSON-LD/面包屑） | 每次部署前必跑 |
| L2 构建校验 | `build.py` 退出码 | 每次改数据/模板 |

| L4 浏览器手工 | 上线清单（功能/视觉/无障碍/禁用 JS 降级） | 每次部署前 |
| L5 上线后监控 | 见 §6 | 持续 |

### 4.2 通过门槛

- **红线（任一不过 = 不许上线）**：L1 断链、外链 noopener、L2 非零退出、禁用 JS 降级失效。
- **严重（登记限期修复）**：L1 其余项、L3 死链、性能超预算。
- **一般（带病上线进整改）**：无障碍非致命、文案细节。
- 已登记豁免（3 条）：裸 IP 政务站、cppcc/cndca 未启用 https（进 §9 DEC 备注，不阻断）。

### 4.3 SEO 基线

- sitemap：13 URL，**手动补**（自动生成方案待授权，DEC-014）；lastmod 待内容哈希自动生成（DEC-014 方案含）。
- 内链绝对路径 + `target="_self"`；外链 `_blank` 全带 `noopener`。
- 不优化负面词、不建门页、外访链接不带品牌搜索词（DEC-006）。

### 4.4 安全与合规基线

- 第三方脚本仅 GA4/百度统计/AdSense（去留待拍板 DEC-014）；引入前过供应链检查（SRI、版本锁定）。
- 全站非官方声明可见；政务频道零广告（DEC-002）；内容五条红线（§7.4）。
- 隐私页为 AI 草稿，法律条文级内容**待执业律师复核**（AI 不越界）。

### 4.5 性能预算

- 根页 HTML gzip ≤ 预算值（当前 19.6 KB 传输，健康）；图片 WebP；首屏第三方请求 ≤ 预算。

## 7. 环节 ⑦ · 收录与内容

### 7.1 收录流程（五步闸门）

```
提交申请 → ① 资质核验（域名归属/备案/仿冒排查）→ ② 合规检查（五条红线）
        → ③ 数据入库（cards.unified.xlsx，英文列）→ ④ build + 校验 → ⑤ 上线 + sitemap 补录
```

### 7.2 核验标准

- 官方入口：域名归属 + 备案信息 + 仿冒预警排查（深度研究专家方案）。
- 民生求助类（心理/法律援助等）：**最严核验档**——官方发布渠道交叉核验 + 复核周期（DEC-008）。
- 收录后季度复核；发现证伪立即降级/挂红标。

### 7.3 外链属性政策（按域名优先级）

同域 > 同族 > 营销 > 评论 > 暴露 > 默认；不设全局 no-referrer；`_blank` 必带 `noopener`。

### 7.4 内容红线（五条，人工守门）

1. 站内政务/民生资讯**只聚合不生成**，发布前人工守门。
2. 不冒充官方、不用官方标识。
3. 收录必须核验（无备案/诈骗预警不收录）。
4. 负面词（代办/代开/加急/包过/贷款/下载器）不优化、不收录。
5. 政务/机构/办事频道页不放广告。

### 7.5 内容策略（吃搜索流量的正道）

- 频道页导语内容化（独特描述，非模板重复）。
- 办事指南类文章（月 2–4 篇，人工撰写 + 审稿闸门，必须有真实官方出处）。
- 内容页内链回导航卡片传权重；不编造来源。
