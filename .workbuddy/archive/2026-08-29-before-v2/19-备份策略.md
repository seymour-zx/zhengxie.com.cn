# 正协导航 · 备份策略（19-备份策略）

> 读者：改造前、季度抽查、需要回档时必读。
> 版本：v1.0 ｜ 2026-08-29
> **治理铁律见 MEMORY「backup.md 第 2 铁律」与 CONVENTIONS §4.4（唯一权威源）**——本文**不复制**铁律，只补：**分层策略、执行步骤、回档演练、有效性验证**。

---

## 1. 备份分层

| 层 | 内容 | 位置 | 周期 | 保留 | 谁负责 |
|---|---|---|---|---|---|
| **L1 版本控制** | 全站源码 + 产物（ADR-012） | Git 仓库（public） | 👤 用户每次提交 | 永久 | 👤 用户 |
| **L2 改造回档点** | 改动前的受影响文件快照 | `.workbuddy/backups/YYYY-MM-DD-<用途>/` | **每次改动前** | 最近 3 个有效备份 | Agent |
| **L3 治理层全量快照** | 全空间逐字符拷贝（方案 C2） | `.workbuddy/memory/backup.md` | 👤 用户下达「备份」指令时 | 滚动保留上一版指针；历史实体存 `backups/` | Agent（受指令触发） |
| **L4 数据源** | `cards.unified.xlsx` / `pages.unified.xlsx` | 随 L1 + 单独副本放 L2 | 数据改动前 | 同 L2 | Agent |
| **L5 线上历史** | GitHub Pages 历史部署 | GitHub | 每次 push | 由 GitHub 管理 | 平台 |

## 2. L2 回档点（最常用，每次改动必做）

### 2.1 目录结构

```
.workbuddy/backups/YYYY-MM-DD-<用途>/
├── MANIFEST.txt          # 必填，缺了视为无效备份
└── <被改动文件的原始副本，保持相对路径>
```

### 2.2 MANIFEST 模板

```markdown
# 回档点 MANIFEST

- 功能/用途：<一句话>
- 时间：YYYY-MM-DD HH:MM
- 执行者（Agent 名称）：<必填，未注明=无效>
- 来源清单：
  - <相对路径 1>
  - <相对路径 2>
- 回档说明：<如何还原——复制到哪、是否需要重跑 build>
- 对应迭代卡：<memory/YYYY-MM-DD.md 的哪一张>
- 状态：active | superseded
```

### 2.3 执行步骤

```bash
# 1. 建目录
mkdir -p .workbuddy/backups/YYYY-MM-DD-<用途>/

# 2. 复制受影响文件（保持相对路径）
cp --parents <文件1> <文件2> .workbuddy/backups/YYYY-MM-DD-<用途>/

# 3. 写 MANIFEST.txt（用上面模板）

# 4. 记时间日志（注明 agent 名称）
```

### 2.4 保留与清理

- **仅保留最近 3 个有效备份**；超出的最旧一个清理前，MANIFEST 的 `状态` 改为 `superseded`。
- 清理动作记入时间日志；批量删除前列清单请用户确认（文件改动铁律）。
- 备份**永不进发布层与资源层**（CONVENTIONS §4.1 铁律 1）。

## 3. L3 治理层全量快照（`backup.md`）

**触发**：用户下达「备份」指令（触发词"备份"）。

**动作**（MEMORY backup 铁律）：

1. 重生成 `.workbuddy/memory/backup.md` —— 全空间所有文件（**不含 `.git/`**，**排除 `changelog.md` 与时间日志**防自引用）的**逐字符完整拷贝 + 来源注释**（方案 C2）。
2. `changelog.md` 追加自上次蒸馏后的新内容（时间日志 → changelog 蒸馏）。
3. 历史版本实体另存 `backups/` 带日期副本；changelog 滚动保留**上一版**指针。

**注意**：

- 仓库 public → 快照内容对外可见（用户已明示接受，CONVENTIONS §1.3）。
- 快照体积大（MB 级），**仅按需生成**，不是每次改动都做。

---

## 4. L4 数据源备份（额外强调）

数据源是整站的真值源，一旦损坏影响最大。

| 时机 | 动作 |
|---|---|
| **改 xlsx 前** | 复制 `cards.unified.xlsx` / `pages.unified.xlsx` 到当次 L2 回档点 |
| **schema 变更前** | 同上，并在 MANIFEST 注明"schema 变更" |
| **每月** | 台账对账（card / link / html），确认数据与线上一致 |

---

## 5. 回档演练（每季度）

**目的**：验证备份真的能还原，而不是"以为有备份"。

| 步 | 动作 |
|---|---|
| 1 | 从 `.workbuddy/backups/` 选一个 `active` 回档点 |
| 2 | 在**临时目录**还原（不要直接覆盖工作区） |
| 3 | 对照 MANIFEST 的来源清单，逐文件校验内容与当前一致（或确认为预期旧版） |
| 4 | 若涉及页面：重跑 `build.py`，确认生成结果与备份产物一致 |
| 5 | 记录演练结果到当日时间日志；失败的回档点标记 `superseded` 并重建 |

> 演练频率：**每季度一次**（与 CONVENTIONS §4.6 文件体检季度项合并执行）。

---

## 6. 有效性验证（每季度抽查）

| 检查项 | 判定 |
|---|---|
| 最近 3 个回档点是否都存在且含 MANIFEST | 缺任一 → 不合格 |
| MANIFEST 是否注明 agent 名称 | 未注明 → 该备份无效 |
| `backup.md` 索引 ↔ 全空间实际文件是否齐全 | 抽查 5 个文件比对 |
| changelog 是否覆盖备份范围内的实际变更 | 抽查 3 条变更追溯 |
| 时间日志是否支撑 changelog 每条记录 | 抽查 3 条 |
| trash 中是否有超 30 天未处理项 | 有 → 确认删除 |

> 完整审计流程见 MEMORY「审计指令」。

---

## 7. 灾难恢复场景

| 场景 | 恢复路径 |
|---|---|
| 单个文件改错 | L2 回档点取该文件覆盖 → 重跑 build（若属生成产物则改数据源） |
| 数据源损坏 | L2 / L4 副本覆盖 → 重跑 build → 全量校验 |
| 误删文件 | L2 回档点 → 若无则 L3 `backup.md` 取内容 → 再无则 👤 用户从 Git 历史恢复 |
| 整库丢失 | 👤 用户从 Git 仓库 clone（L1）+ L3 快照补治理层 |
| 线上发布出错 | 👤 用户 `git revert`（17-部署流程 §3） |

---

## 8. 纪律复述

1. **每次改动前**必须有 L2 回档点 + MANIFEST（02-迭代规则 §3.1）。
2. **受管文件增删改 → 实时记时间日志**（backup 铁律）。
3. `backup.md` **仅在「备份」指令时**重生成，不是每次改动都做。
4. 备份不进发布层/资源层；临时脚本用后即删。
5. 批量删除前列清单请用户确认（文件改动铁律）。
6. 换设备时：`.workbuddy/` 随仓库同步，恢复后**先检查身份文件软链接是否仍有效**（MEMORY 跨设备数据策略）。
