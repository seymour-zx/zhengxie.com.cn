## 一、MEMORY.md 扩展解读（2026-08-25 确立，实时对应 MEMORY 结构）

> 本节是 MEMORY.md 的**扩展版**：MEMORY 只留步骤，本节为每条步骤补充"为什么/背景/决策依据"。新增/修改 MEMORY 条目时，须同步在本节对应小节补解释；本节每小节编号与 MEMORY 章节一一对应。

### 1.1 项目背景（为什么只有一个项目）
- 站点「正协导航」（zhengxie.com.cn），纯静态导航站，GitHub Pages + 自有域名。
- 工作空间 = `D:\Universal Space\zhengxie.com.cn`，`.workbuddy` 随仓库跨设备同步。
- 只有本项目 → 项目级数据是唯一事实来源，无跨项目混淆；跨设备同步靠仓库（git）而非用户级配置。

### 1.2 最高无上铁律——为什么
- **触发语义**：正常注入成功时，MEMORY 全文已完整在上下文里，无需再暂停确认（避免每次开场打断）；只有注入被截断（agent 拿到的 MEMORY 不完整）时才确认，保证"残缺时不盲跑"。
- **三次确认门槛**：本铁律是整个规则体系的根，防任何 agent/会话单次顺手修改稀释它；三次明确同意 = 用户深思熟虑的强信号。
- **3000 软上限由来**：注入上限 3000 字符（系统约束）。曾有两版硬上限提案（写入前自测≤3000、超限先瘦身），用户否决——改为软上限：可超、超了仅记待办，不拦截、不反复精算（降 token 消耗）。

### 1.3 backup.md 第 2 铁律——为什么
- **方案 C2 选型**：全空间逐字符完整拷贝 + 来源注释，优于"仅索引/指针"——信息治理铁律要求"完整复制不指向"，C2 保证任何文件删除/损坏都能从 backup.md 完整恢复。
- **风险已明示**：backup.md 随 memory/ 进 Git、仓库 public → 全空间内容公开。用户 2026-08-25 明确接受"public 仓库下全量公开"，不得再劝阻。
- **实时→备份指令演进**：最初"受管文件增删改→必须重生成 backup.md"，每改一次就跑全空间快照（1.3MB+），token 消耗大；2026-08-25 用户拍板改为"实时记时间日志，仅备份指令时重生成"——快照按需做，证据链由三层（日志/changelog/backup）兜底。

### 1.4 备份/审计指令——为什么
- **触发词约定**：用户说"备份"即执行快照+蒸馏；说"审计"即三重验证。避免每次变更都全量备份。
- **审计三重验证的由来**：backup=内容态（全量镜像），changelog=事件态（变更史），时间日志=原始证据。三者信息类型不同，不能互相"等于"（曾设想过 changelog 蒸馏=backup，不成立——镜像≠日志）；改为验证**覆盖关系**：backup 完整 → changelog 覆盖 backup 范围 → 时间日志支撑 changelog 每条。任一级丢信息，审计即查断点。

### 1.5 时间日志生命周期——为什么
- **最旧日志嵌快照**：历史可追溯需要"当时的备份"作锚点，最旧日志是时间链起点，嵌当时 backup 快照最合理；后续日志只记变更，避免每日快照膨胀。
- **不追溯历史（1乙）**：既有日志（08-24/25）生成于 backup 铁律确立前，无"当时快照"可补，故规则自 08-26 起执行，不补历史。
- **指针不全文（2乙）**：backup.md 1.3MB+，全文嵌入时间日志/changelog 会使其膨胀 ×100；实体存 `backups/` 带日期副本 + 指针（信息治理铁律2 去重指针合法），兼顾可追溯与体积。
- **changelog 滚动保留上一版 backup 指针（3甲）**：changelog 既存变更史又持上一版快照指针，审计时基线可对照；滚动（非固定首次）保证始终有"最近的历史基准"。

### 1.6 强制首读锚点——为什么（含读取分级完整版）
- **顺序锁死**：MEMORY（步骤）→ README（公开层）→ CONVENTIONS（解释层）。先拿步骤再补解释，避免拿错层级。
- **与最高无上铁律的关系**：铁律1 管"异常时是否暂停确认"（注入失败才触发），首读锚点管"常态下按什么序读全"（每次必做）。二者互补：删锚点→注入正常时没人保证读全三文件；删铁律1→注入异常时没人触发确认。不冗余。
- **三级读取（完整版）**：L0 强制首读（MEMORY / README / CONVENTIONS，全读，钉死 3 文件）；L1 按需读（skills/*/SKILL.md 做对应领域前、memory/changelog.md 用户问"某次做了什么"才读）；L2 不主动读（seo-audit-*.md、根 report.md、根 overview.md、artifacts/*、BOOTSTRAP/IDENTITY/USER/SOUL 仅身份重建时用）。

### 1.7 跨设备数据策略三件套——为什么（含权威源约定完整版）
- **技能/记忆一律项目级**：随仓库同步才是权威源，用户级 `~/.workbuddy/` 不跨设备、不随仓库。
- **身份软链**：真实文件在工作空间（随仓库），用户主目录 C:→D: 软链接；换设备需重建（复制→删原→建链接→失败回滚）。开场必查软链，防"本机读的是旧副本"。
- **跨设备权威源约定（核心原则）**：换设备对话时，所有"AI 必须遵守的项目规范"必须落在**随仓库同步的 md 或代码**里，不得只放在非同步位置。
- **权威源清单（全部随仓库同步，均为可读）**：
  1. `README.md`（仓库根）—— 项目总览、决策与偏好总览（唯一权威决策手册）。
  2. `.workbuddy/skills/*/SKILL.md` —— 已注册的项目技能（子页 SOP、SEO 标准等），由 Skill 系统加载。
  3. `.workbuddy/docs/*` —— 项目约定文档（如本文件）。
  4. 代码内置约定：如 `assets/.build/build_homeplus.py` 顶部 docstring「同骨架导航产品页（/directory/）· 框架约定」即为跨设备权威源。
- **禁止**：把"AI 必须遵循的项目规范"作为唯一出处放在**不被同步**的位置（如用户主目录 `~/.workbuddy/skills/` 下的用户级技能、本地未提交文件、会话临时草稿）。
- **自问**：新增 / 修改项目级规则前先问——"这条在另台设备读得到吗？"读不到就别只放在非同步处，落到上述权威源之一或代码里。
- **SEO 专项**：SEO 标准手册已固化为项目技能 `.workbuddy/skills/zhengxie-seo-standard/`，做 SEO 讨论前必读本技能。

### 1.8 文件职责边界——为什么
- MEMORY=步骤（读得快、注入省）；CONVENTIONS=解释（要理解时查）；SKILL=操作流程（执行时载）。互补不重复：MEMORY 讲"数据存哪一级"，CONVENTIONS 讲"规定是什么"，技能讲"操作步骤"。
- changelog 与时间日志：时间日志是 changelog 的时间片段（⊂），changelog 是去重浓缩（∪dedup）；记录范围均 L12（同 backup）。
- **与第四章边界（2026-08-27）**：本节讲治理文档角色分工（元层）；文件物理组织/命名/schema/生命周期/文件体检见第四章（§4.1–4.6），两维度不重叠。本节"L1/L2"指 §1.6 三级读取（L0/L1/L2），与第四章五层目录（L1–L5）是两套编号，勿混。

### 1.9 文件改动铁律——为什么
- 用户对本空间文件有强掌控要求（发生过多次规则修订），首次明确同意前不擅动任何文件；"首次"=agent 首次进入（含对话内切换 agent），同一会话内后续改动已获授权。

### 1.10 Git/同步纪律——为什么（含全停令/冲突裁决/.gitignore 政策）
- **Git 全停令（凌驾一切）**：git 操作（add/commit/push 等**任何 git 命令**）由用户本地处理，agent 只提醒未提交/已修改文件、绝不执行——防 agent 误操作仓库、防跨设备同步冲突。2026-08-25 明确：**含 `git add` 也禁**，agent 不再自动 add。
- **【已废止】同步强制规则（原完整版）**：原"强制同步文件必须 `git add`""每次收口必查并补 add""新会话第一条补 add"等指令，**已被 Git 全停令（含 add 也禁）覆盖，全部失效**。跨设备权威源清单（哪些文件随仓库同步）见 §1「权威源清单」（第48–54行）与「跨设备数据策略 三件套」（MEMORY 第32–35行），不再以 git add 动作表述。
- **严禁进 git（`.gitignore` 政策，仍有效）**：`.workbuddy/backups/`、`__pycache__/*.pyc`、`*.verify.tmp.py` 不得进入 Git 仓库（`.gitignore` 已涵盖）。此为数据卫生规定，非 git 操作指令。
- **冲突裁决（2026-08-25）**：Git 全停令（含 add 也禁）**优先于一切同步/add 指令，最高优先级**。原"add≠commit 不冲突、同步强制要求 agent 主动 add"（旧 5.2 裁决）因此**失效**。若用户明示"本次不要同步某强制文件"，以用户当时指令为准。
- **.gitignore 同步记录铁律（完整版）**：
  - **全文权威载体 = `memory/backup.md`**（通则：受管文件增删改→实时记时间日志，备份指令时重生成 backup.md 比对，见 MEMORY backup 铁律段）。
  - 注：`__pycache__/`、`*.pyc` 不进 Git 原因备忘见 backup.md .gitignore 条目注释（非铁律）。

### 1.11 公开暴露铁律——为什么
- 仓库 public + 页面不暴露仓库地址/.workbuddy 存在：公开是仓库属性，页面防护照常执行（用户确认，二者不冲突）。
- README 是 `.workbuddy/` 外文件、仓库公开 → 必须零内部引用（`.workbuddy/`/CONVENTIONS/真实统计 ID 均不可出现）。

### 1.12 对话翻译铁律——为什么
- 用户指令若只"理解不记录"，跨会话即丢失（发生过口头约定漂移）；强制翻译成 agent 语言落盘（长期→MEMORY、当日→日志、可复用→SKILL），保证约定不随会话消失。

### 1.13 信息治理铁律——为什么（含文档生命周期完整版）
1. **冗余即删**：冗余无效信息视为干扰项，即使无害也删（MEMORY 注入名额有限）。
2. **完整复制不指向**：受管文件记录须完整复制实际内容，防"指针断链后信息丢失"；去重指针除外（backup 历史版本、changelog 上版快照指针）；README 归公开暴露铁律全禁，不归本律。
3. **时间日志兜底**：删除前提=时间日志先记好（实时层）；changelog 定期蒸馏（备份指令时追加），不实时兜底——原"changelog 兜底"因 changelog 不再实时更新而失效（2026-08-25 改）。
4. **5.6 删前回档+确认已失效**：回档职责归 backup 第2铁律（全空间逐字符备份，删后可从 backup 恢复），确认职责归文件改动铁律（首次同意制）；仅保留"禁止裸放 md"核心（处置出口/融合优先，backup 与确认替代不了）。
- **文档生命周期（任务新建 md 处置纪律，堵"裸放 md 漂移"断层）**：
  - 根因：agent 为单次任务新建的 md（方案/计划/审计/纪要）若建完就裸放在 `docs/` 当永久文件，会重新制造"多 md 关联漂移"。故新建 md **默认不是终点**，必须有处置出口。
  - **处置优先级（融合优先，禁止裸放）**：
    1. **融合进权威源后删废料**：方案/计划类 md（如 file-governance-plan、dev-process-plan、execution-rules）执行完后，实质内容并入 `README` / `CONVENTIONS` / `skills/SKILL` 之一，原文件**删除**。
    2. **降级为 L2 归档**：审计报告 / 一次性交付物（seo-audit-*.md、artifacts/report.md、根 report.md、根 overview.md）无规定内容可融合，则明确归 L2 不主动读，可留作归档或删。
    3. **保留为索引层**：提炼型 md（如 memory/changelog.md）有长期检索价值，保留并定为 L1。
    4. **权威源本身**（CONVENTIONS / README / SKILL）保留，是规定唯一归宿。
  - **删除纪律（已精简，2026-08-25）**：原"删前必回档 + 用户确认"已失效——回档被 backup.md 第 2 铁律取代（删后可从 backup 恢复，回档仅作可选手段）；确认被「文件改动铁律」取代。删除只需满足「文件改动铁律首次确认 + 优先融合/降级处置」。
  - **禁止**：任务 md 建完即裸放 `docs/` 当永久文件、不处置（核心断层仍在，backup/确认不能替代"处置出口"）。
  - **实例**：file-governance-plan.md（2026-08-24 任务交付方案）已并入 + changelog + 当日日志，原文件回档后删除，符合本纪律。

## 二、专家转介纪律（🚫 AI 硬边界，任何设备 / 会话必守）

> **原则（用户明示）**：专业的事找专业的专家，不要浪费时间 / 资源消耗却结果不达预期。AI 在工程实现（静态站结构、build 流程、README / SKILL 维护、统计代码接入）上擅长；在需要执业资质、第三方平台策略、专业评审的任务上不擅长且不应越界。

### 必须转专家的任务清单

| 任务类型 | 为什么 AI 不替代 | 应咨询的专家 / connector（WorkBuddy 内） |
| -------- | ---------------- | --------------------------------------- |
| **隐私政策 / 免责声明 / 个保法条文合规** | 涉及法律效力与属地法条，需执业律师复核 | 法律类专家/connector：`同花顺法律AI助手`、`北大法宝·法律智能检索`、`fazhi-law 同花顺法律AI助手`、`yuandian-mcp 华宇元典法律数据`、`pkulaw 北大法宝` |
| **SEO 收录策略 / 统计归因配置** | 百度统计 referer、sitemap 优先级对收录的影响属平台策略，需 SEO 实务经验 | SEO/投放类：`腾讯营销投放`、`wx 相关投放`、`morningstar` 等视具体需求；也可直接咨询百度搜索资源平台 / Google Search Central 官方文档 |
| **视觉设计评审（奢华风是否到位、暗色对比度无障碍）** | 需设计专业判断与无障碍标准（WCAG）核验 | UI/UX 专家（WorkBuddy 内 `ui-ux-pro-max` 等）或人工设计师 |
| **ICP 备案实操 / 国内服务器迁移合规** | 涉及行政流程与属地政策 | 域名服务商（阿里云/腾讯云）官方备案通道，或 `腾讯云 CloudBase` 等国内托管 connector |
| **广告收益优化（AdSense 布局/单价）** | 平台政策与变现策略，AI 只管代码接入不动策略 | Google AdSense 官方帮助中心；投放类专家 |

### AI 在本项目中的明确职责边界

- ✅ **AI 做**：按 SOP 新增 / 调整子页、跑 build、同步 sitemap / 页脚 / README、维护链接规则与统计代码接入（代码层面）、如实把技术实现写进隐私 / 免责草稿（并置顶"AI 辅助、非执业律师意见"声明）。

## 三、页面技术契约（2026-08-24 确立；2026-08-27 合并原三+原四）

> 本章是页面层的**技术契约**：3.1 决定每类页面用什么 JSON-LD `@type`，3.2 决定页面层级心智模型与面包屑怎么走。新增/调整页面时按本章执行。

### 3.1 页面类型 ↔ JSON-LD `@type` 映射表

> 规则：所有页 `isPartOf` 统一回链**站点根 `WebSite`**（`https://zhengxie.com.cn/`），不回链门户页或频道页；页面层级路径用 `BreadcrumbList`（另加）表达，不靠 `isPartOf` 嵌套。
> 自动化页面（根页 + 15 频道页）由 `build_homeplus.py` 的 `build_jsonld()` 生成；手写页（`pages/*`、门户页、404）需手工加。

#### 现有页面映射

| 页面 / 页面族 | 生成方式 | `@type` | 备注 |
| ------------- | -------- | ------- | ---- |
| 根页 `index.html` | build 自动 | `WebSite` | 带 `SearchAction`（站内搜索），`isPartOf` 不适用（自身即站点根） |
| 频道页 `directory/<name>/` | build 自动 | `WebPage` | + `isPartOf`→站点根 + `mainEntity`(ItemList 卡片)；“主题网址导航产品”，与首页同类 |
| 门户/频道导航 `directory/index.html` | 手写 | `CollectionPage` | 罗列各频道入口，本身是"频道的集合/目录" |
| `pages/about` | 手写 | `AboutPage` | 关于页 |
| `pages/contact` | 手写 | `ContactPage` | 联系页 |
| `pages/guide` `pages/overview` `pages/sitemap` `pages/submit` `pages/privacy` `pages/disclaimer` `pages/changelog` | 手写 | `WebPage` | 通用说明/功能页，兜底类型 |
| `404.html` | 手写 | （可不加） | 404 页通常无需 JSON-LD |

#### 未来扩展页面映射（新增页时照此选类型）

| 计划新增的页面类型 | 推荐 `@type` | 说明 |
| ----------------- | ------------ | ---- |
| **博客 / 文章列表** | `Blog` 或 `CollectionPage` | 文章索引页用 `Blog`；单篇文章列表也可 `CollectionPage` |
| **博客单篇文章** | `BlogPosting`（首选）或 `Article` / `NewsArticle` | 带 `headline`/`datePublished`/`author`/`publisher`；资讯类用 `NewsArticle` |
| **问答 / 常见问题** | `FAQPage` | 配合 `mainEntity`(Question/Answer 数组) 触发 FAQ 富结果 |
| **产品 / 工具详情页** | `ItemPage` | 单实体详情 |
| **搜索结果页（独立 URL）** | `SearchResultsPage` | 本站前端筛选无独立 URL，暂不需要 |
| **作者 / 组织资料页** | `ProfilePage` | 个人/组织主页 |
| **标签页 / 分类页** | `CollectionPage` | 一组条目的集合 |

> 选型原则：能用 schema.org 既有语义类型就别用裸 `WebPage`；但也不要硬塞无关类型（如导航站无文章却标 `Article` 会误导）。新增页后同步更新本表。

### 3.2 页面层级隐喻与 BreadcrumbList 约定

#### 3.2.1 建筑隐喻（站点信息架构的官方心智模型）

用户确立的站点层级心智模型，作为一切导航 / 面包屑 / 内链设计的依据：

| 层级 | 对应页面 | 隐喻 | 说明 |
| ---- | -------- | ---- | ---- |
| **入口** | 根页 `index.html` | **大楼正门 / 大门** | 网站的入口。例外：搜索子页面、用户自访子页面、外链直达子页面可不经过它（但仍是站点根 `WebSite`）。 |
| **指示牌（总）** | `pages/overview/`（网站全景） | **入门后看到的全局指示牌** | 入门后第一块总览牌，分发到全站各板块（导航产品 / 博客 / 榜单 / 功能页）。是"全站中枢"，与门户页为**兄弟中枢**，非父子。 |
| **指示牌（楼层）** | `directory/index.html`（频道导航） | **某楼层的指示牌** | 垂类频道的集合入口（"频道的集合/目录"，`@type=CollectionPage`）。与 overview 平列，不是 overview 的子级。 |
| **房间** | `directory/<name>/`（频道页） | **楼层中的各个房间** | 具体主题网址导航产品（`@type=WebPage`）。父级是门户页 `directory/`，再往上是根页。 |

> 关键约束：**overview（总指示牌）与 directory（楼层指示牌）是兄弟关系，不是父子**。不要把"网站全景"塞进"频道导航"的面包屑上层，也不要反过来。两者都直接从根页（大门）到达。

#### 3.2.2 BreadcrumbList 约定（据此出 B 档实现）

面包屑每一级必须是**真实存在、可点击、且与页面可见导航一致**的 URL。套用隐喻：

| 页面族 | 面包屑（可见 + JSON-LD 一致） | 隐喻解读 |
| ------ | ---------------------------- | -------- |
| 根页 | （无面包屑，自身即大门） | — |
| 门户页 `directory/` | 首页 › 频道导航 | 大门 › 楼层指示牌 |
| 国内频道页 `directory/<name>/`（如 bank/stock/gov） | 首页 › 频道导航 › 频道名 | 大门 › 楼层指示牌 › 房间 |
| **国际频道页 `directory/world-*/`（如 world-bank/world-stock）** | **首页 › 频道导航 › 国际XX导航**（例：国际银行导航 / 国际证券导航） | 大门 › 楼层指示牌 › 房间（"国际"作为频道导航内的一个分区，非独立楼层） |
| 9 个 `pages/*` 子页 | 首页 › 网站全景 › 子页名 | 大门 › 总指示牌 › 具体板块 |
| overview 本身 | 首页 › 网站全景 | 大门 › 总指示牌 |

> ❌ **禁止**写法：`首页 › 网站全景 › 频道导航 › 频道名`。理由：overview 不"拥有"directory（兄弟非父子），该链虚构层级，搜索引擎可能忽略甚至判不实。若未来确要在 overview 内把"频道导航"作为下属板块呈现，须先改 overview 页面结构使其真实成立，再调整面包屑。
> ❌ **禁止**把国际频道面包屑写成 `首页 › 外国频道中心 › 国际XX`（除非已落地"完整法"新建独立国际门户，见 3.2.3）。当前采用轻量法，国际频道归属频道导航内的"国际"分区。
> ✅ 若要让"从网站全景也能走到频道"，正确做法是在 overview 页面**放一个可见的"进入频道导航"链接/卡片**（它本就是分发中枢），而非靠面包屑伪造层级。

#### 3.2.3 与 3.2.1 一致的 future-proof 规则

- 新增"板块"（如博客、榜单）时：若它像 overview 一样是**全站分发中枢** → 它的子页面包屑用 `首页 › 网站全景 › 板块名`；若它像 directory 一样是**某类内容的集合入口** → 用 `首页 › 频道导航 › 具体内容`。
- **国际频道（world-*）架构决策（2026-08-24 拍板）**：
  - 采用**轻量法**：不新建独立"外国频道中心"门户页；`world-*` 仍置于 `directory/world-*/` 路径下，作为**频道导航内的"国际"分区**；面包屑统一 `首页 › 频道导航 › 国际XX导航`（如"国际银行导航""国际证券导航"）。
  - **完整法（暂缓，待国际频道数量壮大后再评估）**：若未来外国频道多到需要独立楼层，可新建独立门户（如 `directory/world/` 或顶级 `world/`），届时 world-* 迁入其下，面包屑改为 `首页 › 外国频道中心 › 国际XX`；**必须同步做 301 重定向 + 更新 sitemap**，避免收录掉落（参见 `zhengxie-seo-standard` 技能）。
- 面包屑文字必须与页面里真实可见的导航标签一致（如首页按钮叫"频道导航""网站全景"，面包屑就用这两个词，不另造"导航中心""频道中心"等）。

## 四、文件治理规范（2026-08-27 确立，文档管家起草；重排吸收原六 + 原五§5.2 + 原七§7.7）

### 4.1 五层目录总则（先归层，再命名）

| 层 | 目录 | 内容 | 生命周期 |

| **L1 发布层** | 仓库根 | `index.html` `404.html` `robots.txt` `sitemap.xml` `CNAME` `ads.txt` `favicon.ico` | 线上可见，生成器产出或手写 |

**铁律：**
1. **备份永不进发布层与资源层**——`index.html.bak`、`self_links.bak.xlsx` 一律进 `.workbuddy/backups/`。
2. **临时脚本用后即删**——`_` 前缀只表示「本次会话临时」，不表示可长期滞留；临时脚本不得留仓库根或同步区。
3. **真值源唯一**——同一数据只允许一个权威位置，其余为草稿副本并明确标注。

### 4.2 文件命名通则

| 规则 | 内容 | 示例 |
|---|---|---|
| **时间戳统一** | 一律 `YYYY-MM-DD`（禁止 `20260825_1130` 变体） | `2026-08-27` |
| **分隔符** | 文件名词间用 `-`；程序标识符（脚本/列名/键）用 `_`；不混用 | `项目规范-2026-08-27.md` vs `build_homeplus.py` |
| **大小写** | 代码/数据文件小写 snake_case；文档 md 中文标题式（无空格）；HTML/URL 目录小写 | `check_links.py` |
| **类型后缀** | `.md` `.xlsx` `.py` `.json` `.html` 不许省 | — |
| **序号前缀** | 有序集合用两位数 `NN-` | `38-数据建表专家-2026-08-26.md` |
| **自解释** | 3 秒内能判断「这是什么/谁在用」；禁止 `this.xlsx` 类无意义名 | — |

**分类型细则：**
- **页面/URL 目录**：`pages/<name>/`、`directory/<name>/` —— `<name>` 小写英文单词（URL 友好），中文仅作页面标题。
- **数据源 xlsx**：`self_links.<scope>.xlsx`（scope=`root`/`engine`/`gov`）+ 台账 `<层级>_verification_log.xlsx`（`card`/`link`/`html`）。
- **Python 脚本**：生成器 `build_*.py`；工具 `check_links.py`/`collect_meta.py`；临时 `_临时名.py` 用后即删。
- **文档 md**：`<主题>-<日期>.md`（交付物）或 `<序号>-<角色>-<日期>.md`（答卷归档）；**治理规范融入本节，不裸放独立文件**。
- **备份**：统一 `.workbuddy/backups/<YYYY-MM-DD>-<用途>/`（目录）或 `<原名>.<YYYY-MM-DD>.bak.<ext>`（单文件）。
- **身份文件**：`BOOTSTRAP.md`/`IDENTITY.md`/`SOUL.md`/`USER.md` 全大写为惯例，保留。

### 4.3 数据 schema 一致性

### 5.1 迭代四阶段（每次改动必走；2026-08-24 确立，合并自 dev-process-plan / execution-rules）

> 本节是「怎么跑一次开发迭代」的硬纪律。Git 全停令 / 首读锚点 / 文档生命周期已并入第一章（§1.6 / §1.10 / §1.13）；文件归档与清理见第四章（§4.4）。本节保留迭代四阶段本体。

| 阶段 | 动作（标准动作） |
|------|------------------|
| **1 立项 Plan** | 1.1 明确目标与范围（一句话）；1.2 列改动清单（文件+行号/区段+改前→改后），首次改/删等用户确认；1.3 定验收标准（可观测通过条件） |
| **2 执行 Build** | 2.1 全量备份到 `.workbuddy/backups/backup_<功能>_<YYYYMMDD_HHMM>/` 并写 `MANIFEST.txt`；2.2 按清单改文件（不扩大范围）；2.3 涉及 build 模板/数据源的改动必须重跑 build 重生成根页+15 频道页；2.4 跑标准校验脚本 `assets/.build/verify_site.py` |
| **3 同步 Sync** | 3.1 更新约定/技能（若引出新规则）；3.2 写当日 `memory/YYYY-MM-DD.md` 迭代卡（非流水账）；3.3 确认新增约定落在同步区 |
| **4 收口 Close** | 4.1 写迭代卡（目标/范围/清单/验收/回档锚点）；4.2 清理临时脚本/超期备份；4.3 提示可提交（**只提醒不询问**） |

> 单文件微调也至少走 Plan 清单 + Build 备份 + Close 查跟踪，可合并到一张迭代卡。

### 5.5 必做 / 建议做 / 不建议做 / 禁止做（红绿灯总表）

**🔴 禁止做（红线，任何阶段）**

3. **收录未核验链接**（无备案/域名归属/诈骗预警核查）。
4. **agent 执行任何 git 命令**（含 add）——Git 全停令。
5. **新 md 裸放 `docs/` 当永久文件**——必须融合进权威源或降级 L2。
6. **不传谣发布纪律**：待核实（pending）零主动触达；证伪即降级挂红标；误报 >5% 熔断（#31 建成后适用）。

8. **优化负面词**：代办/代开/加急/包过/贷款/下载器（D4）。
9. **删除首页通用类目 / 剥离流量词**（LOCKED：垂类为主、通用为辅）。
10. **改 build.py `ROOT_META`/`SLOGAN` 常量期望改 meta**——self_meta.json 会覆盖；**手改每页 canonical**——build 自动生成。

1. 外访链接带"正协导航"搜索词（品牌填充=操纵，用户已最终拍板**不带**）。
