## 2. 关键选型记录（含放弃的方案）

### 2.1 前端框架：不用（ADR-006）

| 方案 | 评估 |
|---|---|
| ✅ **原生 CSS + 原生 JS** | 零依赖、零供应链风险、零构建、首屏最快；交互复杂度（筛选/搜索/收藏/滑道）完全够用 |
| ❌ React / Vue | 引入运行时 ~40 KB+ 与构建链，收益为 0（无复杂状态） |
| ❌ Tailwind / UI 库 | 与"设计 token 自持 + 克制视觉"冲突；产物膨胀 |
| ❌ TypeScript | 无构建链则无法类型检查；收益需在 04-组件库规则 契约 + 测试里补 |

**替换触发**：需要状态管理 / 团队多人协作前端 / 交互复杂度显著上升。

### 2.2 数据形态：xlsx + Python 生成（ADR-002）

| 方案 | 评估 |
|---|---|
| ✅ **xlsx 单一真值源 + Python 生成 HTML** | 运营者（非程序员）可直接用 Excel 编辑；单一真值源；生成结果可 diff 回档 |
| ❌ 手写 HTML | 337+ 卡片不可维护 |
| ❌ JSON/YAML + 静态站点生成器（Hugo/Jekyll） | 引入新工具链与主题体系；Excel 对运营者更友好；且需重写全部模板 |
| ❌ 头less CMS / 数据库 | 违背静态站定位（ADR-001），引入后端与运维 |

**替换触发**：卡片总量 > 800、build 耗时 > 30s、需多人并发编辑数据。

### 2.3 构建语言：Python

| 方案 | 评估 |
|---|---|
| ✅ **Python 3 + openpyxl** | 环境已有；标准库足够（html/json/re/urllib）；唯一第三方依赖 openpyxl 成熟稳定 |
| ❌ Node.js 脚本 | 需 npm 安装依赖（xlsx 解析库），引入 node_modules 供应链面 |
| ❌ Makefile / Shell | 逻辑复杂（表头归一化、颜色解析、JSON-LD 生成）不适合 |

**依赖纪律**：构建期第三方依赖**只允许 openpyxl 一个**。新增依赖需在本文 §1 登记并说明不可替代性。

### 2.4 托管：GitHub Pages（ADR-001，⚠️ 高风险待复议）

| 方案 | 评估 |
|---|---|
| ✅ **GitHub Pages**（现状） | 零成本、自动 HTTPS、与仓库一体、push 即部署 |
| ❌ Vercel / Netlify | 同样境外，国内访问无改善；免费额度虽足但无实质收益 |
| 🟡 **国内对象存储 + CDN（OSS/COS）** | 国内访问快、解决百度降权；代价：需 ICP 备案 + 手动配置静态托管与 CDN + 部署流程重写 |
| 🟡 国内云主机 | 运维成本最高，纯静态站不划算 |

**风险**：境外托管导致百度收录降权（SEO Backlog P0）。**替换触发**：备案完成（A5/F1）或百度索引量连续 2 月不增长。迁移必须 301 + 更新 sitemap。

### 2.5 统计与广告：三套并存（ADR-010，⚠️ 待拍板）

| 方案 | 评估 |
|---|---|
| 🟡 **百度统计 + GA4 + AdSense**（现状） | 覆盖国内外数据 + 变现；代价：3 个第三方域拖慢首屏，国内大概率被墙导致超时 |
| 🟡 仅留百度统计 | 首屏最快、数据聚焦国内主战场；代价：失去 AdSense 变现与海外数据 |
| ❌ 自建统计 | 违背静态站定位，运维成本不可接受 |

**待拍板**：01-PRD §9 Q2 / CONVENTIONS §5.7 D-4。拍板后同步 11/14/18 三份文档。

### 2.6 无 Service Worker

`manifest.json` 存在但**未注册 Service Worker**。

- 理由：SW 会带来缓存失效调试成本与"改了不生效"的线上事故风险；导航站内容更新不频繁但要求"改了立刻生效"。
- 若未来引入：**必须**设计缓存版本号与强制更新策略，否则禁止上线。

## 3. 版本与兼容性基线

| 项 | 基线 |
|---|---|
| Python | ≥ 3.9（实测 3.13.12 可用；脚本仅用标准库 + openpyxl） |
| 浏览器 | 支持 ES6+、CSS 变量、`aspect-ratio`、`grid-template-areas`、`100dvh` 的现代浏览器（Chrome/Edge/Firefox/Safari 近 2 年版本） |
| 移动端 | iOS Safari / Android Chrome 近 2 年；响应式断点：手机 2 列 / 平板 3 列 / 桌面 4 列 |
| 降级要求 | 禁用 JS 时页面内容**完整可读可点**（SEO 生命线，不可妥协） |

> 不追求 IE 兼容；不追求"看着像 App"的 PWA 体验。

## 4. 引入新依赖的门槛（新增任何库前必答）

1. **不可替代性**：标准库/现有方案为什么做不到？（说不出 = 不加）
2. **收益量化**：换来什么可观测收益（体积↓ / 速度↑ / 缺陷↓）？
3. **代价清单**：体积、首屏影响、供应链面、维护负担、是否需要构建步骤。
4. **降级方案**：该依赖失效/被墙/停维护时怎么办？
5. **登记**：改本文 §1 表 + 记时间日志 + 走 02-迭代规则 四阶段。

### 特别约束

- **运行时第三方脚本（统计/广告/字体/SDK）**：当前无 CSP，引入前必须过 11-安全审计 §5 检查清单；**国内可访问性是一票否决项**（GA4/AdSense 已因此待复议）。
- **前端 npm 包**：默认拒绝。本项目无打包链，引入 npm 包等于引入整条构建链。
- **CSS/JS CDN 资源**：默认拒绝。全站资源自持，无 CDN 依赖。

## 5. 明确不用的技术（含理由，勿重复提议）

| 技术 | 不用理由 |
|---|---|
| React / Vue / Svelte | 交互复杂度不需要，违背 ADR-006 |
| Tailwind / Bootstrap | 与设计 token 自持冲突，产物膨胀 |
| TypeScript | 无构建链，无法落地类型检查 |
| Hugo / Jekyll / Astro | 需重写全部模板；xlsx 数据源与运营习惯不匹配 |
| 后端（Node/Python Web）/ 数据库 | 违背静态站定位与零运维目标（ADR-001/007） |
| Service Worker | 缓存失效风险 > 收益（§2.6） |
| 前端 CDN 资源 | 全部资源自持，避免第三方不可控 |
| 图片 CDN / WebP 自动转换服务 | 图片总量仅 39.9 KB / 4 个文件，无规模效益 |
